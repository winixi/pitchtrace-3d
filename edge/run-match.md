# 运行一场离线比赛

`run-match` 串联原片准备、曝光重放、场景重建和本地网关提交。运行目录由本场独占。用[比赛配置](match-config.md)指定比赛、标定时间线、名单和对时窗口，在同一 JSON 对象中加入以下字段。

| 字段 | 用途 |
| --- | --- |
| `recordings` 或 `captureConfig` | 二选一。前者是现有 2–8 机位的录像目录，后者是采集配置文件。相对路径按比赛配置文件所在目录解析。 |
| `gateway` | 可选 HTTP(S) 网关基址，例如 `http://127.0.0.1:8766`。省略时只产出本地归档。 |
| `mediaEpoch` | 平铺机位的媒体周期，默认使用 `streamEpoch`。显式分周期的机位沿用录像内的周期名。 |
| `backfillBytesPerSecond` | 历史场景补传的字节速率。默认 0 表示使用可用带宽。 |
| `retentionDays` | 可选正整数，指定本地生成物的保留天数。启用后由留存命令预演及执行清理。 |

例如，已有 `match.json` 和同目录的 `recordings/` 时，在比赛配置中加入 `"recordings": "recordings"`，然后从仓库根目录运行下列命令。首次选择一个新目录或空目录。

```sh
swift run --package-path edge pitchtrace-edge run-match ./match.json ./trial-run
```

`trial-run/media/` 保存逐机位的原片、索引、曝光顺序和缺口文件。`trial-run/scenes.sqlite` 保存 v2 场景、原帧证据、轨迹和事件。`run-state.json` 是可直接读取的运行记录，包含比赛、流周期、本地阶段、摘要和每个网关各项任务的结果。失败时记录 `failedStage` 和 `error`。

## 用采集配置开赛

比赛与采集配置使用相同的比赛 ID。采集尝试依次保存到运行目录内的 `capture-001/`、`capture-002/` 等目录。查看当次的 `health.json` 和各路原片可以定位通道失败。具有有效曝光映射的机位提交到当次的 `recordings/`。已有至少两路就能继续重放和重建；运行状态的 `capturedCameras`、`missingCaptureCameras` 和采集诊断保留实际参与情况。

采集成功但尚无足够的曝光映射时，命令会保留原件和当前阶段。用 `attach-exposures` 向指定的 `capture-…/` 目录补入设备映射，随后重跑原命令。失败的文件输入可从源文件发起新的一次采集。设备输入发生中断时沿用已有原件和曝光映射。原片不足且必须重新采集时，另选新运行目录。

## 重启、复算与上行

同一份输入可重复执行上述命令。运行目录使用文件锁，每次只允许一个编排器写入。命令按内容核对配置、输入录像／采集文件、镜头报告、检测器模型与处理程序，再核对已导出媒体、已生成场景及证据。进程在重建中退出时，重启可从相同录像恢复相同序号，逐帧对照已归档内容。发生变化时需使用新的运行目录，发布不同场景还需指定新的 `streamEpoch`。

本地计算完成后，在原配置加入 `"gateway": "http://127.0.0.1:8766"` 并重跑即可上行。场景和各机位媒体分别执行。一路返回冲突或网关中断时，其余各路仍独立提交；所有已确认项按网关保存。重跑时继续待完成项，已提交的同内容片段和场景可安全重试。更换目标网关后使用新网关的回执。

编排回归覆盖离线完成后追加网关、一条上传失败后恢复、变更输入／输出、目录冲突、机位隔离以及采集产物复用。

```sh
python3 -B edge/Tests/Integration/test_run_match.py
```

运行 `swift build --package-path edge` 后，用以下集成测试启动独立的回环网关。测试用两路 H.264 重建 20 个 v2 场景，先保存在本地，再加载同一目录上行，并分别通过历史查询和曝光定位核对网关归档。

```sh
node --test edge/Tests/Integration/run-match.mjs
```
