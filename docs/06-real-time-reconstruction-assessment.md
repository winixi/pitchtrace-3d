# 场迹 · 数字孪生与多视角姿态驱动方案评估

**评估日期：2026-11-25。** 本文评估「路线 1」对场迹的适用性，给出可纳入当前试点的工作、扩容前需要验证的假设和低延迟实验指标。试点交付口径见[详细需求说明](01-requirements.md)，各阶段放行条件见[落地开发计划](03-development-plan.md)。

## 1. 对项目的推动价值

五层方案与现有 Edge → Live 架构相符。Edge 负责同步采集、空间标定和人球重建，Live 负责接收、归档、分发和网页复核。当前 Edge 是 SwiftPM 骨架，试播网关提供 v1，Three.js 前端已可接收 v1/v2 场景快照并切换机位。正式 v2 网关和按曝光时刻定位原片仍待开发。近期优先把两台同步样机拍摄的真实训练转成 v2 场景帧，在现有网页里展示人球轨迹，并能找到对应触球的两路原片。[项目实现状态](../README.zh-CN.md#实现状态) · [Edge 与 Live 契约](02-technical-design.md#13-两端交付协议)

## 3. 三组需要验证的指标

### 3.1 相机链路与计算负载

- 以 `3840 × 2160 × 60 × 8 bit` 估算，8 位未压缩图像约 **3.98 Gbps／路**，6～8 路约 **23.9～31.9 Gbps**，还需给封包、重传和同时出帧留余量。单路千兆或单个万兆上联无法承载这组原始流。原始 GigE Vision 图像须经过兼容的采集系统，再做图像搬运和预处理。DeepStream 的 NVDEC 解码用于受支持的编码流。相机到 Edge 的局域网带宽、原片写盘和公网场景流各自核算。[Basler 网络参数](https://docs.baslerweb.com/network-related-parameters) · [DeepStream 编解码文档](https://docs.nvidia.com/deepstream/text/DS_plugin_gst-nvvideo4linux2)
- 首期共同闪光建议门槛为跨机位曝光偏差 **P95 ≤5 ms**，另报最大值。对高速球可追加约 **1 ms** 的同步对照，比较不同步对球心误差和触球定位的影响。录像维持采集帧率，推理按同步窗口调度。对照 Mac mini 与替代主机时使用同一组录像和目标质量，记录解码、裁切、推理与组帧耗时、最老待处理帧的年龄、90 分钟持续吞吐及耗电。[首期验收](01-requirements.md#5-试点验收口径) · [边缘性能设计](02-technical-design.md#51-mac-mini-的推理调度与能耗验证)

### 3.2 场景负载与公网带宽

- 23 人 × 17 关节 × 4 个分量 × 4 B，单精度骨骼数值约 **6.26 kB／帧**，还需计入根节点、球、身份、快照头和封装。即使量化到 3～5 kB／帧，30～60 Hz 的纯载荷约 **0.72～2.40 Mbps**。公网观赛目标是 **1 Mbps** 可用下载带宽，稳态建议预算为 **0.8 Mbps**，包含协议与重传。[Protobuf 编码规则](https://protobuf.dev/programming-guides/encoding/) · [项目带宽预算](04-performance-requirements.md#6-工程预算与候选优化)
- 先用项目的 **10 Hz** 发布基线测现有 13 关节、全员可变姿态的编码大小、CPU、附加误差和断线恢复。单独测浏览器渲染帧率。实测应包括正常负载、关键帧、补传和冷启动资源。原片按复核需求访问或上传，统计对应额外流量。[限速验收](04-performance-requirements.md#5-1-mbps-下的验收要求)

### 3.3 曝光到浏览器首次绘制

- **首期交付上限为 5 分钟。** 按现有建议，在 90 分钟实测中统计至少 99% 的预期输出时隙在曝光后 300 秒内首次绘制，并报告实际显示帧的 P50、P95 和最大值。浏览器当前把插值播放时刻回拨约 100 ms，现有边缘技术设计还为未来帧观察预留了时间。[首期验收](01-requirements.md#5-试点验收口径) · [接收器](../live/web/src/receiver.js) · [延迟预算](02-technical-design.md#52-端到端延迟预算)
- **100～200 ms 是后续局域网实验目标。** 建议记录曝光、收帧、解码、组帧、推理、融合、归档与分发、浏览器绘制的时间点，用共同时间基准或同屏拍摄校验。实验可先测人球基础状态，采用 P95 ≤200 ms，并同步披露缺帧、超期和轨迹质量，再加入全员姿态。根据耗时分布调整批处理等待、融合窗口和插值缓冲，使用同一输入测完整链路。本项目尚无支撑 100～200 ms 的实拍数据。[项目测时方法](03-development-plan.md#4-验收分工与样本口径) · [TensorRT 性能测量](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)

## 4. 从实拍联调到扩容

1. **两路样机联调。** 选两个独立支架，录制共同闪光、近远端跑位、交叉跑位、地面传球和高球。保存曝光时间和独立空间检查点。用现有网页播放实拍生成的 v2 快照，并按曝光时刻找到两个机位的对应原片。提交按场区统计的可见率、米制误差、轨迹 ID 切换和分段耗时。[首轮场勘与放行条件](03-development-plan.md#3-按周实施与放行条件)
2. **四路完成首期试点。** 根据样片确定四机位的镜头、摆位与计算配置，推进采集录制、人球轨迹、正式 v2 网关、姿态和同步原片复核。简模用于早期检查，首期的骨骼、号码和动作功能按需求验收。用目标人数和光照条件完成 90 分钟实测，并按 1 Mbps 下载条件验证纯三维观看。[详细需求](01-requirements.md#5-试点验收口径) · [1 Mbps 验收](04-performance-requirements.md#5-1-mbps-下的验收要求)
3. **按瓶颈扩容。** 若目标在原片里不可辨，优先调整镜头和摆位。若拼抢区双视角可见率或三角化夹角不足，补试有针对性的机位。若视觉质量达标但处理持续积压，先测调度与模型配置，再以同一录像对照 NVIDIA 平台。高速球精度、全员高频姿态和战术叠加以实拍轨迹质量为基础逐项验证。[开发风险和处理条件](03-development-plan.md#5-风险触发条件与处理责任)
