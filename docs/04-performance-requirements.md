# 场迹 · 性能要求：三维直播带宽与流畅性

**更新日期：2026-11-24。** 本文补充[详细需求说明](01-requirements.md)中的 R08、R09、R10，重点约束公网 Server 与局域网 Mac mini Edge 部署下的两段流量：**单场比赛的 Edge → Server 上行**，以及 **Server → 单个 Web 用户的下载**。服务器多观众总出口、相机到 Edge 的局域网码流分别核算，不混入上述两个指标。

## 1. 目标与当前判断

- **用户明确的目标：** 在可用下载带宽为 **1 Mbps** 的网络上，Web 用户能够流畅观看三维比赛。“1M”在本文统一解释为 **1,000,000 bit/s，约 125 kB/s**，不是 1 MB/s，也不是每秒渲染一帧。
- **配套工程目标：** 纯三维模式下，单场比赛的 Edge 上行也应控制在 1 Mbps 内；两条链路分别限速、分别验收。持续传输以不超过 0.8 Mbps 为预算，为波动、重传和恢复保留余量。
- **优先评估的交付方式：** 公网直播只传结构化三维数据，实拍原片在 Edge 本地保存。是否最终仅传三维、如何提供公网原片复核，尚未定案；不得默认四路实拍必须实时占用场内公网出口。
- **当前判断：** 现有 22 人全骨骼 JSON 合成估算在 10 Hz 下已约 1.35 Mbps，超过 1 Mbps，不能作为满足目标的方案。真实 Edge 链路尚未实现，也没有完成 1 Mbps 网络下的端到端验收。

1 Mbps 是本次明确的访问目标。下文的 0.8 Mbps 预算、首屏时间、帧率和编码误差等细化指标为**建议验收值**，需在首轮目标设备测试后冻结；修改时保留结果与原因。本文补充网络约束，沿用原有采集精度、缺测语义和端到端延迟要求。

## 2. 计量口径

| 指标 | 计量范围 |
| --- | --- |
| Edge 上行 | 一台 Edge 为一场比赛发往公网的场景、控制消息、心跳、上传请求、重传和补传；启用媒体时再加视频与索引。相机到 Mac mini 的局域网传输另计。 |
| 单用户下载 | 一个浏览器观赛会话收到的三维数据、控制消息、网页、模型、字体等资源；开启实拍时再加实际播放的视频。按首次加载、稳态观看、恢复与回看分别记录。 |
| 验收带宽 | 使用真实 HTTPS/WSS，以网络层 IP 字节计数，包含 TCP/IP、TLS、HTTP/WebSocket 开销及重传。链路层开销单独注明。不能只用 JSON 字符数替代。 |
| 合成估算 | 仅统计 `JSON.stringify` 后的 UTF-8 字节，未压缩，不含协议开销、请求响应、音频、页面资源、重试和补传。用于找出编码问题，不能替代上线验收。 |

使用十进制单位：1 kB = 1,000 B，1 GB = 1,000,000,000 B。所有带宽指实际速率，不以宽带套餐标称速度替代可用带宽。

```text
场景有效载荷速率（Mbps）= 平均每帧字节 × 发布频率（Hz）× 8 ÷ 1,000,000
90 分钟流量（GB）= 持续速率（Mbps）× 0.675
Edge 上行 ≈ 场景上行 + 所有实际上传机位的码率之和 + 协议与控制开销
单用户下载 ≈ 场景下行 + 用户实际同时播放机位的码率之和 + 资源与协议开销
```

若 Edge 原样上传、Server 原样分发同一份场景，有效载荷速率相近；两端协议、压缩、过滤或分档不同，实际速率可不同，仍须独立测量。用户切换六个虚拟机位共用同一份场景，不按六路视频累加。

## 3. 当前数据量基线

### 3.1 估算条件

估算日期为 2026-11-24，基于[比赛生成器](../live/web/src/match.js)、[v1 校验器](../live/web/src/protocol.js)和[v2 场景读取器](../live/web/src/live-frame.js)。代码基点为 `8de2aeb`，工作区包含既有前端修改；下列结果是工作区快照测算，不是发布版认证。

- 当前 v1 演示包含 10 名球员，不发送逐关节骨骼，以动作标签和相位驱动浏览器动画，20 Hz 发布。
- 22 人样本按内置 10 人轨迹循环生成，使用独立轨迹 ID、两队各 11 人，包含位置、朝向、号码、状态、来源机位与置信度。它是数据量样本，不代表真实 22 人识别和追踪已实现。
- 全骨骼样本使用当前支持的 13 个关节，每个关节发送一个四元数 `[x,y,z,w]`；使用随时间变化的归一化合成旋转，避免用全零或单位旋转低估字符串大小。
- 一组将所有数值保留 4 位小数，另一组保留 JavaScript 完整浮点字符串；四位小数只用于估算，不是已经验证精度的编码方案。
- 分别在 10 Hz、20 Hz 下取 60 秒，按平均 UTF-8 字节数换算；所有帧须可被对应校验器或场景读取器接受。

### 3.2 场景有效载荷

| 样本 | 发布频率 | 平均每帧大小 | 有效载荷速率 | 90 分钟流量 |
| --- | ---: | ---: | ---: | ---: |
| 当前 10 人 v1 演示，无逐关节骨骼 | 20 Hz | 1.647 kB | 0.264 Mbps | 0.178 GB |
| 合成 22 人，无骨骼，4 位小数 | 10 Hz | 4.073 kB | 0.326 Mbps | 0.220 GB |
| 合成 22 人、13 关节，4 位小数 | 10 Hz | 16.821 kB | 1.346 Mbps | 0.908 GB |
| 合成 22 人、13 关节，4 位小数 | 20 Hz | 16.821 kB | 2.691 Mbps | 1.817 GB |
| 合成 22 人、13 关节，完整浮点 | 10 Hz | 31.897 kB | 2.552 Mbps | 1.722 GB |
| 合成 22 人、13 关节，完整浮点 | 20 Hz | 31.902 kB | 5.104 Mbps | 3.445 GB |

当前演示或“无骨骼”样本低于 1 Mbps，不能据此认定全员骨骼直播达标。发布频率是网络状态更新频率，浏览器应通过插值独立渲染，不能把 10 Hz 直接当成 10 FPS 的合格观看体验。

### 3.3 与传统 720p 的两段链路对比

统一用三维数据 **1.35 Mbps**、每路 720p **3 Mbps** 举例；每个视频源由发送端上传一次，观众按所看内容下载。3 Mbps 对照来自 [Twitch 官方 720p/30fps 编码建议](https://help.twitch.tv/s/article/broadcasting-guidelines?langage=en_US&language=en_US)（核对日期：2026-11-24）；该指南的 720p/60fps 对照为 4.5 Mbps。720p 分辨率本身不限定码率，运动、编码器和画质要求均影响实际值。

| 情况 | Edge／传统发送端 → Server | 单个 Web 用户下载 | Edge／发送端 90 分钟流量 | 用户 90 分钟流量 |
| --- | ---: | ---: | ---: | ---: |
| 传统单路 720p/30fps | 3 Mbps | 3 Mbps | 2.03 GB | 2.03 GB |
| 本项目仅三维数据 | 1.35 Mbps | 1.35 Mbps | 0.91 GB | 0.91 GB |
| 三维＋上传一路 720p，用户仅看三维 | 4.35 Mbps | 1.35 Mbps | 2.94 GB | 0.91 GB |
| 三维＋上传四路 720p，用户仅看三维 | 13.35 Mbps | 1.35 Mbps | 9.01 GB | 0.91 GB |
| 三维＋上传四路 720p，用户看三维及一路实拍 | 13.35 Mbps | 4.35 Mbps | 9.01 GB | 2.94 GB |

以上是未优化三维样本与固定视频码率的算术对照，未计音频和协议开销，也不是后续设计预算。只观看三维时约比 3 Mbps 的视频少 55%，但仍超过本次 1 Mbps 门槛。

若上传的是[技术设计容量示例](02-technical-design.md)中的四路各 8 Mbps 原片，视频上行就有 32 Mbps、90 分钟 21.6 GB；加上述三维流约为 33.35 Mbps、22.51 GB。四路上传量不会因为单个用户只看一路而减少；用户下载则仅累加实际同时播放的内容。

## 4. 传输模式与媒体边界

| 模式 | 公网传输内容 | 与 1 Mbps 目标的关系 |
| --- | --- | --- |
| 纯三维直播，优先评估 | 位置、朝向、骨骼、身份和缺测状态、必要事件；原片本地保存 | 两段链路都按低带宽预算设计，单用户必须能在 1 Mbps 下载条件下流畅观看。当前尚未实现达标编码。 |
| 三维＋用户主动打开实拍 | 三维数据加选中视频；Edge 上行按实际上传机位累加 | 视频单独标明额外带宽与流量，不纳入“1 Mbps 三维观看已达标”的结论。低带宽模式默认不自动加载或预取实拍。 |
| 按需或赛后上传原片，候选方案 | 实时仅三维；事件片段、索引或整场原片以后上传 | 上传任务限速，与实时数据隔离；无剩余带宽时暂停补传。具体检索、授权与复核交付方式待设计。 |

本地原片仍用于算法复算与证据核验。试播网关已用测试视频验证 fMP4 归档和按曝光时刻同步复核。Edge 的实拍采集与自动上传仍待实现。公网部署时 R10 的原片回看、授权访问与同步复核范围待定。[本地原片联调](../live/server/README.md#v2-原片归档与同步复核)

## 5. 1 Mbps 下的验收要求

基线为一场比赛、22 名球员、全部具备当前 13 关节的可变姿态；兼测空场、丢球、未知号码与局部关节缺测。测试使用 1 Mbps 的可用带宽上限，不要求在任意低于 1 Mbps 的网络下仍保持相同画质和流畅性。

| 编号 | 指标与建议验收值 | 计量方式 |
| --- | --- | --- |
| P01 | 单用户在 1 Mbps 下载限速下完成连续 90 分钟三维观看；稳态每个 10 秒滑动窗口平均速率 ≤0.8 Mbps，1 秒窗口速率 P99 ≤1 Mbps | 计入观赛页所有相关请求、背景资源、重传与恢复流量；冷启动单列，仍在 1 Mbps 限速下测试。不能只测场景 WebSocket。 |
| P02 | 单场纯三维 Edge 上行按同样的 1 Mbps 限速、0.8 Mbps 稳态预算验收 | 包含上传封装、认证、心跳和重试；窗口按 1 秒步长取样，关键帧、事件密集时段和恢复补传都要覆盖。 |
| P03 | 场景发布基线 ≥10 Hz；前台可见页面每秒渲染帧数 P5 ≥30 FPS | 正常网络段按秒统计，连续 90 分钟；记录目标设备、分辨率、画质和浏览器，不以网络到帧率代替渲染 FPS。 |
| P04 | 正常网络段无持续超过 1 秒的非预期画面停滞，累计停滞时间 ≤观看时长的 1% | 以持续运动片段测量；排除用户主动定格和注入的完全断网，其他拥塞不能作为排除理由。 |
| P05 | 网络传输、浏览器缓冲与首次绘制按正常负载约 2 秒估算。第一阶段按 R09 验收，曝光后 300 秒内首次绘制的预期输出时隙占比 ≥99%，另报实测 P95 | 网络段从 Edge 发布可用结果到浏览器绘制计时；完整延迟按原 R09 统一物理时钟实测，不能只用播放缓冲时间替代。 |
| P06 | 冷缓存首次可交互三维画面 ≤8 秒，首屏关键资源实际传输量建议 ≤500 kB | 从导航开始计时，Server 已有当前有效场景；包含连接、认证、下载、解析、解码和 GPU 初始化。先可交互画面与完整模型就绪时间分别记录。 |
| P07 | 热缓存首次三维画面 ≤3 秒；完整模型在相同限速下最终可用，不可无限推迟 | 热缓存仍需真实建连并取得当前有效快照；完整模型就绪时间先报告实测值，再冻结门槛。渐进资源不得挤占 P01 的持续预算。 |
| P08 | 切换虚拟机位、跟随球员和定格不重复下载整套场景或模型，不重建比赛数据订阅 | 在同一已加载场景内操作；首次确需加载的额外资源计入下载预算并记录。 |
| P09 | 编码解码附加位置误差 P95 ≤0.02 米、骨骼旋转误差 P95 ≤1°；报告最大值及关键触球样本 | 与编码前同一输入逐帧比较，不与原识别误差混算；压缩不得破坏轨迹身份、时间、丢失／预测状态和可缺测语义。 |
| P10 | 网络恢复且鉴权成功后建议 ≤5 秒绘制当前可用快照；总流量继续受限，不无限积压实时队列 | 模拟 Edge 外网中断、Server 重启和浏览器断线；当前状态先于历史，补传旧帧不回退直播时间。 |

P01 的 1 Mbps 可用网络条件是核心门槛；0.8 Mbps、P03–P04、P06–P10 中的细化数字为建议值。P05 沿用[原需求与验收口径](01-requirements.md)，上述网络优化不能放宽它。

**首次加载也是性能缺口。** 当日工作区 `live/web/dist/index.html` 为 12,056,839 B，约 12.06 MB；在 1 Mbps 下仅传输的理论下限约 96.5 秒，尚未计握手和解析。该大小是工作区构建产物快照，发布前需重测实际压缩传输量。只优化每秒场景流，不能证明首次访问已经流畅。

## 6. 工程预算与候选优化

以下是每条纯三维链路的初始预算，不是已达到的性能结果。两端可以使用不同编码，但不能把大流量从一段隐藏到另一段。

| 项目 | 建议持续预算 |
| --- | ---: |
| 位置、朝向、轨迹与对象状态 | 0.10 Mbps |
| 全员骨骼 | 0.40 Mbps |
| 必要事件、身份／名单增量、应用控制与心跳 | 0.10 Mbps |
| TCP/IP、TLS、HTTPS/WSS 封装与正常重传余量 | 0.20 Mbps |
| 稳态总计 | 0.80 Mbps |
| 距 1 Mbps 的剩余空间，用于受控突发与恢复补传 | 0.20 Mbps |

应用有效载荷合计目标为 0.60 Mbps：10 Hz 时平均约 7.5 kB/帧，20 Hz 时约 3.75 kB/帧。完整关键帧可以更大，但必须经限速与调度，在上述网络条件下满足流畅性和恢复要求。

候选优化包括：

1. 有界精度的数值编码，避免完整浮点字符串；使用紧凑字段、骨骼索引或二进制编码。以每个四元数分量 16 位举例，22 人 × 13 关节 × 4 分量 × 2 B = 2,288 B/帧，10 Hz 仅骨骼原始值约 0.183 Mbps，20 Hz 约 0.366 Mbps。此数未含帧头、位置、状态、关键帧或协议开销，不能直接作为达标结果；需验证四元数归一化、符号连续性和 P09 的误差。
2. 静态身份、名单、骨骼拓扑按版本发送；动态状态使用有基准的差分与周期完整关键帧。新用户、重连和丢失差分基准时必须能恢复，不能用只发送变化却无法独立解码的样本报告压缩率。
3. 比较通用压缩与二进制方案的真实线速、CPU、延迟、内存和恢复成本。不能预设压缩率，也不能只报告一个重复静止姿态的理想值。
4. 保持位置、球和关键动作的时间质量；按优先级分配骨骼更新，浏览器独立插值渲染。若拟降低部分关节频率，必须报告其对动作与接触复核的影响，不能通过删除全员骨骼、减少人数或无限延迟换取达标。
5. 分离首屏资源和完整模型，提供可用的初始画面，按版本缓存并按剩余带宽渐进加载资源。首屏不能依赖先下载完整离线演示包；后续下载仍计入 P01。
6. 上传与补传使用有界队列、持久化待办和总速率调度。连接复用、帧合并等策略要实测封装成本；等待批次产生的延迟计入 P05。

破坏性编码或字段变化须按[现有协议边界](02-technical-design.md#edge-live-contract)版本化，并先补齐双方可解码的契约样例。本文仅提出性能约束与候选方案，未修改接口、数据格式或现有实现。

## 7. 限速、断网与恢复测试

默认不自动请求 HLS 播放列表、视频片段或媒体预加载。实拍需要用户主动开启并显示额外网络需求；1 Mbps 验收会话必须记录实际零媒体请求，而不是仅把视频元素隐藏。

Edge 外网断开时，本地采集与录像按磁盘留存策略继续，持久化待上传的三维结果。恢复后先发当前完整快照，再以剩余带宽补传历史；带宽不足时延后历史或原片，不阻塞采集和实时发布。不可删除本地证据来伪装无积压；缺口、待办数量与保留期限须可见。当前这些 Edge 能力仍待实现。

| 测试组 | 条件与检查内容 |
| --- | --- |
| 对照组 | 不限速，记录同一输入、同一模型的编码前后数据量、画质和渲染基线。 |
| Edge 上行 | 仅将 Edge 公网出口限为 1 Mbps，Web 不限速；测 P02、P05 与上传排队。 |
| Web 下载 | Edge 不限速，仅将单用户公网下载限为 1 Mbps；分别测冷缓存、热缓存和 90 分钟观看。 |
| 两段同时受限 | Edge 上行与 Web 下载分别限为 1 Mbps，保证是两段独立瓶颈，执行完整 22 人全骨骼测试。 |
| 波动与丢包 | 在两段限速基础上，分别增加每段 100 ms RTT、0–50 ms 额外单向随机时延及 1% 丢包；记录配置、随机种子和重传。该组参数为建议值，须与干净限速组分别报告。 |
| 断网与恢复 | Edge 外网完全中断 60 秒、重启 Server、断开浏览器，分别恢复；观察当前快照、关键帧、限速补传、幂等和直播时间。注入区间不计正常停滞，但恢复时间单独验收。 |
| 状态与峰值 | 空场、未知号码、丢球、身份更正、22 人同时运动、快速变向与射门、事件密集、流周期切换；关键帧与恢复突发均不得遗漏。 |

所有正式结果使用固定录像或可复现输入、冻结的编解码器、真实 HTTPS/WSS 和目标浏览器。合成样本先用于协议与流量评估，仍需真实录像／现场数据验证姿态质量和原 R09。32 人等扩展负载另报，不能用低于基线人数的演示替代。

每份报告必须附：代码与契约版本、输入样本、硬件与浏览器、分辨率和画质、限速与丢包位置、传输压缩配置、计量层次、逐秒字节数、10 秒窗口分布、CPU／内存、FPS、停滞、首屏与完整模型就绪时间、编码误差、端到端延迟、恢复与积压曲线。1 Mbps 持续 90 分钟的理论总量为 0.675 GB；0.8 Mbps 稳态预算约 0.54 GB，启动和补传须结合实际会话单列并计入总量。
