# 场迹 · 落地开发计划

**目标**　在一块约定尺寸的真实足球场，第一阶段以 2 台摄像头起步，可扩展至 8 台或更多，每个支架一台，配合一台 M6 Mac mini 完成 MVP 试点。观众能在现场曝光后 5 分钟内看到对应三维画面，复核员能从一次传球或铲球跳回同步原片。交付依据是[详细需求说明](01-requirements.md)的 R01–R12，模块和接口见[技术实现方案](02-technical-design.md)。

直播前端已整合内置演示、WebSocket v1/v2 快照、场景归档回放和按曝光时刻复核原片。v2 场景、片段与时序索引已用固定样例联调。下一步接入真实机位输出并验证现场对时与播放偏差。[直播前端](../live/web/) · [两路原片联调](../live/server/README.md#v2-原片归档与同步复核)

## 0. 当前进度与优先级

**以下为 2026-11-25 的历史基线。当时核对的版本为 `7260c3a`。** 三维观赛演示可运行，本地 v2 软件联调已通过，实拍试点处于 G1 场勘与可行性验证阶段。仓库内还缺两机位实拍、曝光对时和独立检查点的结果，更多机位投入以 G1 评审为准。

| 模块 | 已验证的仓库基线 | 当前缺口 |
| --- | --- | --- |
| Edge | 双机位离线录像输入已用生成样例打通 v2 原片归档与浏览器复核。支持 2–8 机位或更多扩展。 | 取得带可核验曝光记录的实拍样片，接入相机、标定、检测和三维融合。 |
| Live Server | 源码和打包版各通过 5 项测试，覆盖 v1 回归及 v2 场景归档、分页、原片三件校验、曝光定位和重启恢复。 | 公网设备与观众权限、Edge 自动上传待实现。 |
| Live Web | 19 项测试通过，单文件可构建。此前已在 Chrome 用两路测试视频验证三维回放和按曝光时刻切换原片。 | 实拍同步、端到端延迟和限速观看待验收。 |

**2026-11-26 软件进展。** Edge 已用可生成的双路录像验证按曝光重建、独立机位隔离、身份复算、持续归档和恢复上行。架构支持 2–8 台或更多摄像头扩展。完整运行入口、各模块的输入和验证方法见 [Edge 使用说明](../edge/README.md)。下面的现场放行条件继续单独计量。

现场线先用两机位样片测对时和可见率（G1），再验证更多机位采集（G2）。软件线已用固定样例打通本地 v2 场景通路。两线将在实拍传球中串起人球重建、v2 观赛和按曝光时刻定位原片（G3）。

Edge 的模块输入输出、各周负责人和首轮双机位取证任务见 [Edge 需求与开发计划](07-edge-development-plan.md)。

沿用 10 Hz 场景发布基线。现有估算中，22 人、每人 13 关节的 JSON 有效载荷约 1.35 Mbps。当前离线 HTML 约 12.1 MB，在线演示的一次 HTTP 下载约 5.86 MB，按 1 Mbps 仅传输响应体就约需 47 秒。公网版需分别测稳态上行、稳态下载和冷启动。首期仍按曝光到首次绘制 300 秒验收，100～200 ms 留作后续局域网实验目标。[在线演示](https://winixi.github.io/pitchtrace-3d/) · [网络性能要求](04-performance-requirements.md) · [实时还原评估](06-real-time-reconstruction-assessment.md)

## 1. 排期假设与关键路径

**建议排期为 12 个开发周，另留 2–4 周现场迭代余量。** 估算假定三名全职工程师、一处能重复进场的场地、两次完整外场测试，以及可用于开发与评测的授权录像。相机交期和场地档期可能延长日历时间。第 2 周依据远场像素、跨机位曝光同步和 Mac mini 基准调整范围与日期。

| 角色 | 主要责任 | 试点投入假设 |
| --- | --- | --- |
| A · 边缘与设备工程师 | 场勘、设备接入、对时、录制、性能和故障恢复 | 1 人全职 |
| B · 视觉与几何工程师 | 标定、轨迹融合、球、骨骼、读号、动作评估 | 1 人全职，复杂模型或标注量在第 2 周复估 |
| C · 全栈与交付工程师 | 数据契约、档案、网关、观看与复核、验收脚本和发布 | 1 人全职 |
| 场务、教练／裁判、测试与标注人员 | 进场安装、组织脚本动作、提供独立标注、复核争议样本 | 按场次排班，两人独立标注，分歧由第三人裁定 |

关键路径依次为**拍清并对齐多路画面 → 建立共同坐标 → 跨机位稳定追踪人球 → 重建姿态与事件 → 90 分钟端到端实测**。网关、观看端、归档和标注工具可用录制数据并行开发。现场首个成果是用两处支架拍一段真实传球，在浏览器显示轨迹并跳回同一脚触球的原片。后续可按需扩展至更多机位以提升覆盖范围和精度。

## 4. 验收分工与样本口径

| 验收对象 | 对应需求 | 主验收人 | 必须归档的证据 |
| --- | --- | --- | --- |
| 多路输入、时间和场地尺度 | R01、R02、R03 | 场务与 A，B 独立检查几何 | 配置、录像、共同闪光序列、独立空间检查点误差。不同机位数量的配置分别记录。 |
| 人球位置与身份 | R04、R05 | B 与标注人员 | 全部分母、覆盖率、近／远端误差、身份切换、读号混淆和人工修订。 |
| 动作与复核 | R06、R07 | B 与教练／裁判 | 标注约定、关节检查、事件类别明细、证据机位、缺证案例。 |
| 显示、端到端延迟 | R08、R09 | C 与 A | 暂停切机位对照、时钟误差、目标设备上的延迟分布、超期和掉帧时隙。 |
| 归档、权限、检索导出 | R10、R11、R12 | C 与场务 | 同步跳转清单、权限矩阵、恢复演练、删除结果、可复算导出样例。 |

1. **分样本。** 工程调试、阈值选择和最终验收按场次隔离。起步准备两次脚本化训练及至少一场独立比赛。五类动作各争取 30 个独立正例，并保留无动作时段和易混淆负例。稀有动作可组织安全演练；演练结果与自然比赛分别列报。样本不足的类别标记待验。
2. **建真值。** 两名标注人员在实拍原片上标出球员、号、球、可见性和事件区间。位置与骨骼误差用独立参考装置或人工标注的已标定独立视角求值，记录参考误差。无法获得可信三维真值的片段只评二维重投影与覆盖，不计入三维精度通过项。
3. **算指标。** 可见目标覆盖率分母取人工可见目标时隙；球员 ID 切换按被跟踪球员的总在场时间归一化。姿态误差采用球场坐标，报告样本量和参考误差。事件用同类、同参与者且起始时间相差不超过 1 秒的一对一匹配；带球等持续事件另报区间重叠率。定义在 G1 冻结，变更需同时重算基线。
4. **测时延。** 以冻结的发布频率生成预期时隙；计入过载、超期、缺失和断流。每个时隙的截止点为曝光后 300 秒，采集结束后观察至末个时隙截止，将缺帧和迟到帧计入失败时隙。正常和人为故障时段分别统计，报告整体结果。第 11 周用同屏高帧率记录或可追溯时间码，独立验证曝光到浏览器首次绘制的端到端时间。
5. **归档清单。** 每次验收产生一次运行编号、Git 提交、模型和标定版本、场地与硬件信息、样本划分、指标、失败片段索引和复核结论。原始比赛资料按授权范围留在试点存储；仓库发布可共享的测试样例、说明和汇总指标。

## 5. 风险、触发条件与处理责任

| 观察到的风险 | 何时介入 | 处理与复测 |
| --- | --- | --- |
| 远端丢球、读不清号码 | G1 像素测量或人工判读失败 | A、B 重选角度和焦距，近端特写与远端覆盖协调；重走远端禁区和边线。覆盖缩水须更新承诺的场地范围。考虑增加机位数量改善覆盖。 |
| 曝光漂移或支架移动 | 闪光不同步、重投影残差持续变大 | A 检查触发、网络和时钟映射；B 隔离异常机位并重新标定。复验快速长传与高点。 |
| 单台 Mac mini 热机后积压 | 连续负载下队列年龄持续增长，预计无法在曝光后 300 秒内显示 | A、B 分段定位，先调度姿态／OCR、复用解码缓存，再优化模型。若仍不足，报告目标机的实测上限与替代配置，重新走 G5。考虑减少机位数量或调整推理频率。 |
| 人员交叉导致串号，遮挡后“假球”继续飞 | G3/G4 身份或失球样本错误 | B 调整跨机位匹配和预测时限；C 在网页展示缺测，复测同一片段及独立比赛。 |
| 铲球接触被挡住 | 两个独立机位均看不清关键瞬间 | 复核员标记证据不足；保留事件和原片。B 单独统计此类覆盖，不将动画当作判罚依据。 |
| 原片存储不足、网络中断或临时断电 | 剩余录制时长低于剩余赛程或分段写入失败 | A、C 告警、保护已归档段，恢复后修复索引并标出时间缺口；演练时核对已提交片段校验值。 |

源码与打包版均通过网关回归。Chrome 从 `/?match=trial-01` 验证空场、丢球、未知号码、时钟重置与重启重连，并回放迟到帧。两路红蓝测试视频分别以 30 fps 和 25 fps 验证原片定位。在 `00:25.000` 切换时，两路均命中同一曝光时间，片段内 seek 位置分别为约 0.317 s 和 0.540 s。实际相机对时与公网鉴权按后续阶段交付。

基线复跑使用打包版网关导入两路生成的 fMP4 测试视频。在 `00:25.000`，两路定位接口均返回曝光差 0 µs，所得播放列表及媒体可读取。在 `00:01.200`，两路均返回缺片 404。测试视频的曝光时间由样例预设。

### Edge 双机位录像输入（生成样例已验证）

已从[两路测试视频生成器](../live/server/tools/review-sample.mjs)导出初始化文件、片段和逐帧曝光映射。Edge 输出 220 帧和四个片段。重复导入后网关仍只保存四个片段。Chrome 在 `00:25.000` 暂停切换 A、B，两路均显示曝光差 0 ms，并在 `00:01.200` 显示缺片提示。接下来换入有曝光记录的实拍录像。[联调步骤](../edge/README.md#用生成样例联调)

| 顺序 | 工作与负责人 | 完成条件 |
| --- | --- | --- |
| 1 | A 在 SwiftPM 增加离线录像输入，读取两路 fMP4 及逐帧曝光映射。 | 每路保留机位 ID、原始帧号（样片提供时）、PTS、时基和曝光 UTC。按曝光时间确定性重放；缺映射、时间倒退和缺帧可定位到具体机位和帧。 |
| 2 | A 用固定输入验证媒体产物，C 用本地网关验证接收。 | 每路产生初始化文件、片段和逐帧索引，索引中的字节数与 SHA-256 均与实际片段一致。回归覆盖两路不同帧率、相同曝光但不同 PTS、缺口和相同内容重复提交。 |
| 3 | C 用已有 v2 场景样例核对两路回放。 | 在同一暂停场景时刻，两个机位命中各自预期帧，缺片清晰可见。A 与 B 随后接入首批实拍曝光记录，为 G1 提交对时和可见率结果。 |

回归使用 `swift test --package-path edge --disable-xctest`，网关归档和曝光定位回归位于 `live/server`。

### 现场线 · 两机位可行性与录像输入

- Edge 已提供 `audit-sync`。用标注的共同闪光帧生成逐事件曝光偏差、配对数、未配对数、P95 和最大值。生成样例用于回归，现场评审使用实拍曝光记录。[标注格式和运行步骤](../edge/README.md#g1-双机位曝光对时)
- A 与场务确认目标场地、授权、留存与样机，测量四个候选位置。先在两个独立支架录共同闪光、近远端与交叉跑位、地面传球和高球，记录相机序号、曝光时间来源、原始帧号、帧率、丢帧及版本，报告曝光偏差 P95 和最大值。第一轮以 P95 ≤5 ms 为建议门槛。
- B 记录独立地面和高点检查点，提交远端球和号码的人工可辨样本、高球与脚踝的分区双视角可见率，以及首次三角化误差。A 用样片准备 SwiftPM 录像输入的固定回归数据，保留两路原片及曝光时间映射。
- G1 评审使用覆盖图、对时与几何结果、目标 Mac mini 上的解码和模型初测，确认四路开发条件及排期。软件闭环通过后，用首次实拍生成的人球快照接入同一条 v2 通路，按曝光时间核对两处原片，作为 G3 实拍联调的输入。
